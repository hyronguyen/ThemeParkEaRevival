# Remaining issues and next milestones

Completed milestones: native asset/layout inspection; 730 original 3D assemblies; 3,363 decoded animation tracks and four code-verified idle animations; static park assembly; a user-authorized offline playtest with NPC navigation/queues, ride placement, desktop UI and local progress saves. A faithful Theme Park port is **not complete**. See `playtest_mechanics.md` for provisional rules and `model_formats.md` for original-asset evidence.

Next recover attraction definitions and exact model placement/orientation, then original camera, material modifiers and draw queues. No decorations or owned rides have been guessed into the scene.
2. **Animation bindings:** Track format, 33 ms timing, quaternion interpolation and delta composition are recovered. Four idle bindings are verified in code; map the remaining groups and operating states without matching by appearance/node count alone. Pirate ship model 409 remains static until its group is proven.
3. **Additional asset formats:** RGB565/RGBA5551 are resolved for model textures through iPad3 image-table metadata. Extend validation across other device variants; recover Apple CgBI conversions, audio PAC metadata/raw sample encoding and Android DBPF entries. The initial inventory's 5,288 opaque BFC records includes model/animation resources now understood by later manifests; it is not a current unresolved count.
4. **Runtime park state:** Static layout is available, but actual owned attractions, active territories, guest state and complete WorldInstance/LoadData schemas are not. Eight recovered layout tables preserve remaining unnamed fields for further work.
5. **Gameplay:** The user authorized provisional rules to make the offline playtest usable. Placement, connected-path BFS, guest states, queues, capacity-limited batches, close/reopen, pause/speed and saves now work. Original guest needs, navigation weights, placement gates, collection, maintenance, upgrades, quests and progression still require recovery. Do not present provisional rules as original behavior.
6. **Offline state:** Trace service response consumers and locally computed rules. Remote configuration and historical park responses are missing. Build independent local state only where behavior is understood; no fabricated server-success layer or entitlement bypass.
7. **Android comparison:** Matching expansion OBB packages are absent. Do not download from EA services without authorization. Existing DEX is useful for semantic recovery even without assets.
8. **Fidelity baseline:** A user-supplied 16:59.69 iPad gameplay MP4 is available and 17 frames have been sampled. Paths, canal dividers and bridges visually corroborate the static scene. Next compare individual rides and continuous motion. The recording's exact game build is not established; platform/version differences remain possible. See `gameplay_reference.md`.
9. **Prototype limitations:** The game uses a new desktop UI/camera, not the original UI. Guests have one appearance. Castle riders are visible with provisional choreography; other rides hide passengers; seat/boat attachment and original operating animations are the main next visual tasks. Transparent ordering/effects remain approximate. The older layout-preview save is camera/selection only; the new `TPPLAY3` game save (with TPPLAY2 import) stores simulated progress and is tied to the current layout/catalog.
10. **Packaging/compatibility:** The EXE expects `extracted/` in the project root and its own location under `build/`. No installer or redistributable proprietary-asset bundle was created. Test additional Windows versions, DPI settings and machines after further runtime work.
